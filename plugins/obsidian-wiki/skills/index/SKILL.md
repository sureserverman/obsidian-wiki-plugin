# Vault Index

Generate `<vault>/index.md` — a machine-readable, human-scannable digest of every page
in the Obsidian vault. The index lists each page's title, path, tags, topic mentions,
one-line summary, and last-updated date. Other tools (notably the `vault-context`
plugin used from project repos) read this file to find vault pages relevant to whatever
they're working on, without having to grep the whole vault.

The index is **derived data**: it can always be regenerated from the vault's pages.
Hand-edits are pointless — the next run overwrites them.

## Preconditions

- Resolve the vault path. If the cwd is the vault, use that. Otherwise call
  `${CLAUDE_PLUGIN_ROOT}/scripts/resolve-vault.sh` (env var → `~/.config/obsidian-wiki/config.json`
  → fallback `<vault>`).
- `CLAUDE.md` and `log.md` must exist at the vault root. If not, the vault has not been
  bootstrapped — point the user at the obsidian-wiki README's bootstrap section.

## Build the index

**Always run the deterministic builder.** Do not hand-roll the walk, and do not
delegate it to a subagent (see "Why a script, not delegation" below). The builder
reads every page in one complete pass — no token limits, no truncation, identical
output for identical input:

    python3 ${CLAUDE_PLUGIN_ROOT}/scripts/build-index.py --vault <vault> \
        [--category <Dir> ...] [--dry-run]

**Categories.** If you omit `--category`, the builder auto-detects them: every
immediate subdirectory of the vault holding at least one `.md` file, minus
infrastructure dirs (`raw/`, `Portfolio/`, `.obsidian/`, dotted dirs). Read the
vault's `CLAUDE.md` schema first; if it declares an explicit category set — or one
the heuristic would get wrong — pass each with a `--category` flag instead of relying
on auto-detect. Never hardcode a fixed list of categories.

The builder skips `Home.md`, `index.md`, `CLAUDE.md`, and `log.md` by basename, and
never descends into `raw/` or `.obsidian/`.

**Portfolio integration edges.** `Portfolio/` stays out of category auto-detection
(it is tracking data, not wiki pages), but the builder runs one dedicated pass over
every `Portfolio/<area>/<project>/integration.md` and emits them under a
`## Portfolio Integrations/` section. Each entry's `topics` carry the declaring
project slug plus every `depends_on`/`impacts` target, and its `summary` lists those
edges — so the `vault-context` matcher can surface an inter-project edge from either
end. Vaults with no such files produce byte-identical output (the section is omitted).

The builder owns the walk, per-page extraction, assembly, the idempotency compare,
and the write. It prints stats to stdout — `TOTAL_PAGES`, `STATUS`, and on change
`CHANGED_BLOCKS` / `ADDED` / `REMOVED` with path lists — which you use for the log
entry and report. Pass `--dry-run` to preview the diff without writing.

## What the builder extracts (contract)

For each page the builder pulls these fields. This documents the output contract —
the builder implements it; you do not extract by hand:

| Field | Source | Fallback |
|---|---|---|
| `title` | YAML frontmatter `title:` | filename without `.md` |
| `path` | path relative to vault root | required |
| `tags` | YAML frontmatter `tags:` (list or comma-separated) | empty |
| `topics` | proper-noun tokens in body (capitalized, ≥4 chars, ≤30 unique per page) | empty |
| `summary` | first sentence of body, OR a `## TL;DR` block if present, OR the line right after the H1 | empty string |
| `updated` | YAML frontmatter `updated:` | file mtime as `YYYY-MM-DD` |

**Topic extraction is fuzzy by design.** Pull capitalized tokens that look like proper
nouns (tools, protocols, projects, places). Filter out: page-internal headings, common
English words that happen to be capitalized at sentence start, and tokens shorter than 4
characters. Cap at 30 topics per page so the index file stays bounded.

**Summary length is one line.** Strip markdown formatting. If the first sentence is
longer than 200 characters, truncate at the nearest word boundary and append `…`.

## Index file format

Write to `<vault>/index.md`. **Full rewrite** every run — never patch in place.

```markdown
# Vault Index

Auto-generated by /obsidian-wiki:index on YYYY-MM-DD. Do not hand-edit.
Re-run after ingesting new sources.

Vault: <vault path>
Pages indexed: <N>

## Architecture/

### [[Page Title]]
- path: Architecture/Page Title.md
- summary: <one-line summary>
- tags: tag1, tag2, tag3
- topics: Topic1, Topic2, Topic3
- updated: YYYY-MM-DD

### [[Another Page]]
- path: Architecture/Another Page.md
- ...

## Gotchas/

### [[...]]
...
```

Group by category dir. Inside each category, sort pages alphabetically by title for
stable diffs across runs.

If a field is empty, write the field anyway with an empty value (`tags: `). Downstream
parsers expect a fixed set of keys per entry.

## Idempotency

The builder performs this for you — it compares byte-for-byte before writing and
reports the outcome as `STATUS`:

- File does not exist → creates it (`STATUS=new`).
- File exists and differs → overwrites it (`STATUS=changed`, with `CHANGED_BLOCKS`).
- File exists and is byte-identical → does not write at all, preserving mtime
  (`STATUS=identical`).

## Log append

Append a single entry to `<vault>/log.md`:

```
## [YYYY-MM-DD] index | regenerated (N pages, M changed)
```

Where `N` is total pages indexed and `M` is the count of pages whose blocks differed
from the previous index. If the file was unchanged, write `(N pages, no changes)`.

## Report

Tell the user, in a few lines:

- Vault path
- Total pages indexed
- Pages whose entries changed (or "no changes")
- The path of `<vault>/index.md`

If a downstream tool (like `vault-context` from a project repo) prompted this run,
mention that the index is now ready for it.

## Why a script, not delegation

Earlier versions delegated the walk + extraction to the `vault-scanner` subagent
(haiku) for cost. **Don't.** On a large vault that pass hits token limits and
degrades silently: it truncates mid-vault, returns blank fields, and miscounts pages
— which would shrink and gut the index, the opposite of regenerating it. The
deterministic builder has none of those failure modes and is faster anyway. The only
work left in-session is the judgement around it: resolving the category set from the
schema, appending the log entry, and reporting. Reserve `vault-scanner` for genuinely
read-heavy *judgement* tasks (e.g. lint heuristics), never this mechanical digest.

## Common pitfalls

- **Indexing `raw/` or `.obsidian/`.** Never. Those are not wiki pages.
- **Indexing `index.md` itself.** Skip it explicitly — re-indexing your own output is
  a fast way to thrash.
- **Fabricating tags.** Tags come from frontmatter only. If a page has no `tags:`,
  write an empty `tags:` line. Do not guess based on content.
- **Hand-rolling the walk or delegating it to a subagent.** Always run
  `scripts/build-index.py`; it is the single source of truth for extraction.
- **Hardcoding categories in the invocation** instead of letting the builder
  auto-detect or passing `--category` flags derived from the vault's `CLAUDE.md`
  schema. Read the schema first.
- **Patching `index.md` in place.** Always write the whole file. Stable sort makes the
  diff small.
- **Skipping the log append.** The log is the audit trail; index runs must be visible
  there alongside ingest, lint, and the rest.
- **Writing on every run even when nothing changed.** Skip the write if the new content
  is byte-identical, so the file's mtime tracks real changes.
